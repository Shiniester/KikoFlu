# Android 播放器性能报告

同一 FLAC 内跳转后无声的根因为 Media3 对空 SEEKTABLE 的解析缺陷。Android
升级至 Media3 1.8.0 后，原始文件通过真实播放器进度条跳转与 120 秒连续播放，
用户已确认跳转后声音和进度正常。详见下方“FLAC 播放进度跳转”。

2026-09-17，以 v4.4.16（`2704a5a`）为基线。Android 原始文件直播放消除了
大 WAV/FLAC 的整文件复制：下载 FLAC 的请求至 READY 中位数从 3731ms 降到
99ms，WAV 从 4384ms 降到 173ms。字幕跟随帧耗时 P95 从 21.001ms 降至
14.482ms，改善 31.0%。连续请求由同一个协调器处理，只有最新目标可以提交
曲目、队列索引、媒体信息和会话记录。性能验收尚未全部通过，具体结果如下。

- Flutter 3.44.7 / Dart 3.12.2 / just_audio 0.9.44。五轮动画与换源性能数据使用
  Media3 1.6.1；本次 seek 回归使用经用户批准的 1.8.0，其他依赖保持不变。
- 测试包名为 `com.meteor.kikoeruflutter`。seek 使用应用私有测试目录中的素材
  副本，保留手机上的用户原始音频；报告保存在主机，不提交真实音频或文件名。
- 音频触感反馈关闭。每轮启动前 thermal status 为 1 或 2，未更改系统显示模式。
- 动画预算按每个场景开始时 Android 当前 Display 刷新率计算，本次 UI 场景为
  60Hz，即 16.667ms。音频轮次的 Flutter 启动刷新率不用于动画验收。
- 素材：512MiB PCM WAV、用户提供的 473201145 字节 FLAC、两者的完整缓存，
  以及三首约 5MiB 的小 WAV。中文/日文路径和同名字幕另有设备用例。
- 基线使用独立源码副本，只加入同一份测试和测量入口，生产行为保持 v4.4.16。
  每组五轮，进程每轮重启；首次展开和重复操作分开记录。
- 表内时间单位为 ms。音频每种大文件和离开场景 n=10；P95 采用
  `ceil((n-1)×0.95)`，n=10 时等于最大值。

完整步骤见 [运行文档](player-performance.md)。本地原始报告保存在
`build/player_performance/reports/`，聚合数据为
`build/player_performance/final_summary.json`。公共文档使用匿名素材标识。

## seek 恢复代码回归

Android 本地文件和完整缓存的 seek 错误通过 `playbackEventStream` 接收。
just_audio 0.9.44 的 Android 实现只在 READY 完成 seek 回调，原生错误不会结束
该回调；派生的状态流丢弃错误，单独切换 play/pause 也不会重新准备音源。
服务现在为本次 seek 设置 8 秒等待上限，在错误或无有效回调时通过请求协调器
重建一次原音源，并在加载时传入目标位置。正常 seek 保持原路径。

错误订阅持续覆盖当前曲目的本地 seek；seek 返回后发生的错误会暂停失效
音源，保留源和位置供再次播放恢复。恢复停止、准备和取消清理分别设 8 秒上限；
准备超时实际取消加载，原始停止与加载均结束后才放行新曲目。清理仍未结束时，
当前请求返回失败并撤掉加载状态，后续请求有界等待同一屏障。

- 本机 seek 契约回归 24 项通过，覆盖正常跳转、错误事件、超时、同位置跳转、
  旧 READY 状态、连续拖动、暂停/播放、停止/新曲优先级、停止失败后的继续切歌；
  另覆盖 seek 回调同时或之后的错误、恢复停止/准备超时、旧加载迟到成功或失败、
  等待清理时连续换曲，以及完整缓存超时后重试不删除文件或回退网络。
- 与连续切歌、Android 后端、会话恢复、播放历史和会话存储合计 62 项通过。
- 契约测试将同一等待上限注入为 100ms，以确定性挂起和迟到回调验证超时行为；
  生产上限仍为 8 秒。
- seek 修复及 Profile 场景的 Dart 静态分析、Android arm64 Profile APK 构建通过。
- Profile 入口提供 `--seeks`，分别检查大 WAV/FLAC 及完整缓存正常播放后的
  正向和反向跳转，记录状态、耗时和诊断。

## FLAC 播放进度跳转

“我的 → 已下载”的本地音频通过 `file://` 原始路径交给 Media3。故障素材为
473201145 字节、96kHz、24-bit、双声道 FLAC，包含一个长度为 0 的 SEEKTABLE
元数据块。Media3 1.6.1 在跳到 25% 后约 4.3 秒报出
`Playback stuck buffering and not loading`，在同一位置重载仍无法准备完成。
这与 [Media3 #2327](https://github.com/androidx/media/issues/2327) 一致。

Android 所有 Media3 组件统一固定为 1.8.0，使用上游忽略空表并回退二分查找的
修复。Flutter、just_audio、播放器外观和交互保持不变。服务的有界错误恢复继续
处理原生失败；该恢复机制的 Fake 契约测试不能替代实际 FLAC 解析回归。

同一台手机保留原始空表（offset 86 为 `0x83`，长度为 0），通过真实播放状态、
Mini Player 路由和生产 Slider 的指针手势执行 25%、80%、10% 跳转：

- `seek_fixed_ui_2`：原始 FLAC 与 512MiB WAV 共 6 次跳转全部通过。FLAC 从
  手势开始至 READY 为 478–558ms，至目标后推进至少 500ms 为 1006–1068ms；
  随后一秒继续推进 1012–1017ms，未出现播放错误或恢复重载。
- FLAC 跳转后连续播放 120 秒，进度推进 120002ms。两次 AudioFlinger 快照中，
  同一活动 96kHz 音轨的服务端帧计数持续增长，未出现 underrun。
- 用户实听确认：“跳转后声音和进度都正常”。用户同时澄清 WAV 故障未经验证，
  本次 WAV 作为后端升级的回归素材。
- `candidate_seek_regression_1`：下载 WAV/FLAC 及两者完整缓存共 12 次真实
  进度条跳转全部通过；与实听轮次合计 18 次。59 次成功音源加载（含初始加载）
  覆盖超过 50 次切换，四种加载中 A/B/C 连续请求均只发布 C，无错误且缓存保留。
- 62 项相关契约回归及 4 个变更 Dart 文件的静态分析通过。
- Android arm64 Profile 和常规 Release APK 构建通过。
- 常规修复版 `4.4.0-seek-fixed`（versionCode 2002）已安装并正常启动，
  使用 `lib/main.dart`，不再自动运行测试。外部测试素材目录已移除；完整缓存
  用例创建的两项缓存仍由应用缓存管理，原始音频保持不变。

本地证据位于 `build/seek_device/reports/`，故障基线为 `seek_before_2.json`，
修复后的实听轮次为 `seek_fixed_ui_2.json`。`positionAdvancingMs` 包含手势及
至少 500ms 推进等待，不与旧脚本的 seek 返回时间直接比较；上述数据不替代
Media3 1.6.1 下的五轮动画、加载及换源性能结果。

## 限制与后续

未通过项为动画逐场景的回退/卡顿门槛，以及完整缓存和稳定播放后离开大文件的
25% 收益门槛。测量只覆盖本台 Android 手机；未改变
其他平台的 MPV/Darwin 路径处理。原生加载仍需更细的解码器计时，才能定位离开
音源的进一步优化；拖拽交接需要单独定位构建/绘制尖峰并保持 Hero 和手势语义。

本次 seek 修复已完成该故障文件的真机跳转与实听；尚未重新采集 Media3 1.8.0
下的五轮动画性能数据。
