# Commit release automation

The post-commit hook queues the exact commit SHA, pushes that SHA to the current branch's configured upstream (or `origin` with the same branch name), and asks the release planner whether the commit warrants a release. A remote `main` target uses the stable all-platform workflow; other remote branches use the Android Beta workflow. The planner follows the [release automation policy](../../.codex/skills/release-automation/SKILL.md), including the latest published stable release as the version baseline and no release when changes are not releasable. Stable releases can use PATCH, MINOR, or MAJOR as the policy specifies; Beta versions use the next stable patch and an increasing `-beta.N` suffix.

The worker stores its shared queue and log under the repository's common Git metadata directory at `kikoflu-auto-release`. Turn commits created with a `turn-commit-*.index` temporary index wait for a matching `{head, branch}` acceptance file from the turn-commit helper before push. That acceptance is written only after the real index was installed. Missing acceptance expires after two minutes and is reported in `node scripts/commit-release.cjs status` and the worker log.

Each push uses an explicit SHA refspec without force. If the remote branch already contains the SHA, it is treated as pushed without moving the branch backward. The worker can push newer queued commits while an earlier release is being planned or built, but selects and dispatches releases in queue order. It waits for each dispatched workflow to finish before planning the next version. A dispatch whose result is uncertain blocks later release planning until it is inspected; the worker does not retry an ambiguous dispatch and risk starting a duplicate release.

The planner runs `codex exec` with a read-only sandbox, ephemeral session, disabled Codex hooks, and the schema in `scripts/release-plan.schema.json`. It receives the current release skill, baseline commit, and exact target SHA, and is instructed to inspect source through `git diff` and `git show` at those commits rather than from the current working tree. GitHub calls use REST API version `2026-03-10`; workflow dispatch includes `commit_sha`, so the target branch's workflow definition must accept that input and check out/tag that SHA. A rejection is logged as a failure; the worker never falls back to releasing a different branch tip.

## Local use

Run `node scripts/commit-release.cjs install` from the primary checkout to set its absolute `.githooks` directory as `core.hooksPath`. The installer makes the hook executable and refuses to replace another configured hook path or hide active hooks in `.git/hooks`. Linked worktrees use that same primary-checkout hook path while all Git operations use the worktree that made the commit.

Use `node scripts/commit-release.cjs status` to inspect queued jobs, including push failures, blocked turn commits, and workflow outcomes. The hook remains inactive until `install` is run after review and the required workflow input changes are present on the target branches.
